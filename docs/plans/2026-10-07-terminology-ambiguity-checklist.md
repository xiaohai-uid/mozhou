## 1. Context Receipt 的三个中文名【建议执行】

**现象**：同一个对象，活跃层同时有三个中文名。

| 名字 | 处数 | 证据 |
|---|---:|---|
| **凭证** | 41（仅 `packages` 实测）+ `apps/web/server` 数十处 + **移动端文案** | `context-compiler/src/receipt-file.ts` 全篇「不可变凭证」；`apps/web/src/mobile/hubs/InspectorHub.tsx:77,120,126`「上下文编译与凭证」；`worksRoutes.ts:2`「装配凭据」 |
| **收据**（GLOSSARY 规范词） | **4** | 全部是上一轮我改的：`draftStream.ts:72,235`、`context-compiler/README.md:3,10` |
| **凭据** | ~130 | 绝大多数指**密钥凭据**（正确用法）；但 `projection.ts:13`「续跑**凭据**」、`compile-step.test.ts:212`「恢复**凭据**：…盘上**凭证**取回」把它当 receipt 用 |

**为什么是歧义**：代码、API（`/api/receipts`）与移动端文案一直说「凭证」；权威表说「收据」。**上一轮的"统一"把仅剩的 4 处改成权威表说法**，等于把唯一分歧点钉住，方向与代码相反。

**建议裁决**：规范中文名设为 **上下文凭证 (Context Receipt)**，并**强制带「上下文」限定词**；`凭据` 只保留「密钥凭据」义。

**代价**：GLOSSARY 改 1 条 + 回退我造成的 4 处。代码/API/界面**零迁移**。

**需要你拍板的点（反方理由）**：「凭证」与「凭据」只差一字且都涉安全语义，同一文件里可能同时出现（`providerSettings.ts` 的「凭据」= 密钥 vs `receipt-file.ts` 的「凭证」= receipt）。**正因为如此才要强制限定词**；若你认为一字之差风险不可接受，另一条路是把 ~150 处迁到「收据」——成本高一个数量级。

**不做的后果**：权威表与代码长期各说各话，新写代码的人无从判断该用哪个。

## 2. 作品 / 书 / 小说 —— 作者的同一部创作有三个名字【建议执行】

**现象**：同一实体在同一层同时叫三个名字。

| 名字 | 用法 | 证据 |
|---|---|---|
| **作品** | UI 主用、导航一级 | `WorksView.tsx:2,54,107`「我的作品」「作品信息」；`CapabilityChannels.tsx:13` `{ id: 'works', label: '作品' }`；`MobileTabBar.tsx:40`「作品」 |
| **书** | 建书 / 书库 / 切书 / 书名 / 本书 | `WizardOverlay.tsx:25`「先给**这本书**一个可以启航的名字」；`:27` `field: '作品名'`（**同一向导里两个名字**）；`BookshelfView.tsx:94,107,157`「本地书库」「先建书」；`TopBar.tsx:59`「本地书库」 |
| **小说** | 题材 / 他人作品 | `WorkbenchView.tsx:248` placeholder「输入**小说书名**」；`NovelBreakdownView.tsx:69`「小说拆解」；`PublicSite.tsx:72`「所有**小说**正典」 |

**代码侧**：类型是 `Book`，路由却是 `/api/works`，视图目录 `apps/web/src/works/` —— 英文也不统一。

**为什么是歧义**：一个向导里标题写「这本书」、字段标签写「作品名」、占位符写「小说书名」；作者读到的是三个词指同一个东西。

**建议裁决**：

| 词 | 定位 |
|---|---|
| **作品** | 规范实体名（用户可见的一级名词） |
| **书** | 只留在**已冻结的复合词**：书库、建书、切书、书稿、书名（作为字段名） |
| **小说** | 只用于**题材**与**他人作品**（小说拆解、对标小说、小说文本） |

**代价**：集群 186 处，其中需要改的是**同一语境里混用的那部分**（如向导同一屏、面板标题与按钮冲突处），**不是 186 处全改**。需要先做一次逐处分类，再定改动集。

**需要你拍板的点**：「建书 / 书库 / 切书」已进 UI 与文档多年，是否值得动？我倾向**不动**，只把**同一语境内的混用**统一。

**不做的后果**：不影响功能，但用户与后续维护者持续在同一屏看到两个名字。

## 3. 门 / 守卫 / 检查 —— 阻塞条件有三个名字【建议执行，但需逐条判类】

**现象**：同一类东西（阻塞式前置条件）在活跃层有三种说法。

| 词 | 处数 | 例子 |
|---|---:|---|
| **门** | 多 | `proseRoutes.ts:878`「两道**门**」；`SSRF 门`；`continuity gate` → 连续性门 |
| **守卫** | **171** | `proseRoutes.ts:878`「相位**守卫**」（**与"两道门"同段**）；`proseRoutes.ts:32`「committed 前置守卫」 |
| **检查 / 拦** | 多 | `检查`（GLOSSARY §2.2 已是规范词）；`拦截` |

**最刺眼的证据**：`proseRoutes.sessionComplete.test.ts:238` 写成「**门守卫**」——两个词拼在一起。而 `proseRoutes.ts:878` 同一段里既说「相位守卫」又说「两道门」。

**根因（必须说清）**：前几轮清扫把「门禁」改成「守卫/检查」，**消歧动作本身制造了新歧义**。

**为什么不能直接全局替换**：`packages` 的 104 处「守卫」里，有一批是 **TypeScript 语言概念**，与领域阻断条件无关，改了就是错：

| 属于 TS 语言概念（**不改**） | 属于领域阻断条件（**建议改「门」**） |
|---|---|
| `reviewCapability.schema.ts:433`「运行时**类型守卫**与校验器」 | `proseRoutes.ts:32`「committed 前置守卫」 |
| `benchmark/src/metrics.ts:51`「形状**守卫**」 | `chapter.ts:1209`「写前哈希…双重守卫」 |
| `bookRequest.ts:91`「把 `number` 窄化掉的**守卫**」 | `compaction.ts:319`「双前置**守卫**」 |
| `receipt-file.ts:37`「文件名合法性**守卫**」（防路径穿越） | `projection-rebuild`/`database.ts`「版本**守卫**」（fail-fast） |

**建议裁决**：

| 场景 | 用词 |
|---|---|
| 确定性阻断的通过条件 | **门 + 限定词**（相位门 / 写前哈希门 / 前置门 / 版本门） |
| 不阻塞的验证动作 | **检查**（GLOSSARY §2.2 既有） |
| TypeScript 类型窄化 / 运行时形状校验 | **守卫**（保留，属语言词汇，不进 GLOSSARY） |

并给 GLOSSARY §2.2 补一条：**「守卫」在墨舟产物中只指 TS 类型窄化，不得指领域阻断条件。**

**代价**：需逐条判类。粗判 `apps/web/server` 67 处中多数属领域；`packages` 104 处中 TS 语言概念占相当比例。**无法用一次替换完成**。

**需要你拍板的点**：是否接受"守卫"只保留 TS 语言义？若接受，需一次逐处分类（我可以先出分类表再改）。

## 4. `Scene` / `scene` —— 一个英文词两个不相干的对象【本轮不执行，仅登记】

**现象**：

| 义 | 位置 |

**建议裁决**：界面那个改名为 **场景偏好 (Scene Preference)**；目录 `shell/scene/` → `shell/scene-preference/`。

**代价**：代码改名（目录、模块、标识符），**必须过图谱门**（impact / detect-changes / check）。

**用户未选此项**——登记待裁决。

## 7. 版本 —— 章 revision vs 发布 version【只补 GLOSSARY】

`chapter.ts:1168`「预期**版本**契约」= 章 revision；`package.json` version = 发布版本；`StyleProfile vN` = 画像版本。三者都以「版本」出现。

**建议**：GLOSSARY 明确 **版本 (Version)** 只指发布版本与画像版本；章的那一层一律写 **revision（章版本号）** 或复用既有 **章节提交** 语境。**代码不动。**

## 8. 候选 —— 四个义【只补 GLOSSARY】

GLOSSARY 只登记了 **候选事实 (Candidate Fact)**，且明令「中文一律写"候选事实"，不得只写"候选"」；但代码里裸「候选」遍地，且至少四个义：候选草稿（`draft-candidate.ts`）、候选事实、候选条目（`ActivationEvidence` 的召回候选）、路由候选。

**建议**：GLOSSARY §1.1 补一条通则——「候选」必须带限定词（候选草稿 / 候选事实 / 候选条目），裸用即为错误。**代码不动**（量大且多为注释）。

## 9. 技能 (Skill) vs 能力 (Capability)【只补 GLOSSARY】

GLOSSARY「能力 (Capability)」的 `_Avoid_` 列了 `Skill`；但 UI 写「启用此**技能**到写作流」（`CapabilitySquareView.tsx:212`），同时 `CapabilityRecipe`、`SkillRun`、`.agents/skills/` 并存。

**建议**：GLOSSARY 明确二者分工——**能力**是任务级抽象契约（`PROSE_DEAI` 等），**技能**是作者可见的可启用方法论单元（能力配方实例化后的运行时形态）。二者不是同义词，`_Avoid_` 行需相应拆开。**代码不动。**
