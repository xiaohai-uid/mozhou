# 墨舟分层写作 UX Spike 设计规格

## 目标

验证一个不推翻旧产品模型的 UX 收敛方案：保留“作品世界上下文 + AI 共创 + 可检视生产系统”三根骨架，只调整信息层级与出现时机。

本次是隔离原型，不接真实后端，不进入生产，不修改 `master`。

## 产品假设

墨舟不是通用 AI Chat + Editor。作者真正需要同时获得三类信息：

1. **当前作品世界**：我正在写哪一本书、哪一章，关键人物/世界观/章节在哪里。
2. **当前写作决策**：这一章要发生什么，AI 给了什么候选，我是否接受。
3. **系统可信度**：AI 读了什么、当前进行到哪一步、质量/连续性是否阻塞、内容是否已经提交。

上一轮 A/B/C 的问题是把第 3 类信息削得过多，产品退化成通用写作壳。本轮不再做这种减法。

## 信息层级

### L1 常驻：写作上下文

- 左侧只保留当前作品相关内容：作品、章节、人物、世界观、大纲。
- 中央为当前章节和 AI 共创主路径。
- 顶部保留生产阶段，但降低视觉权重：完整 8 阶段仍可读，当前阶段最突出。

### L2 情境出现：系统证据

右侧 Inspector 保留四个领域视角：

- 质量门：当前生成是否可继续。
- Story Brain：当前故事状态。
- 装配看板：本次生成读取了什么。
- 变更影响：当前改动是否影响后文。

默认只展示“当前最相关”的摘要，不把所有证据同时展开。生成候选后自动把质量门提升为当前证据；用户主动点击可看完整上下文或 Story Brain。

### L3 二级：全局能力

扫榜、书源、拆解、风格蒸馏、技能广场、任务、同步、会员等全部可达，但进入“全部能力”抽屉，不在写作时常驻占据视觉重量。

## 状态契约

- AI 输出先成为 `Candidate`，正文不改变。
- 用户“接受”后进入 `Accepted / Active Draft`，仍未 durable commit。
- 用户显式“提交本章”后进入 `Committed`。
- `Candidate → Accepted → Committed` 三态必须在 UI 上可辨认。
- 质量、上下文、连续性状态不能只靠颜色表达。

## 交互原型 D

### 左栏

- 墨舟品牌 + 当前作品。
- 章节列表常驻，当前章高亮。
- “故事上下文”三项：人物、世界观、大纲，显示数量/摘要。
- 底部“全部能力”按钮打开全局能力抽屉。

### 中栏

- 章节标题 + 保存/提交状态。
- 轻量对话上下文：墨舟先问、作者意图。
- 当前正文可编辑。
- AI 输入固定在底部。
- 生成后出现候选卡；接受不会立即显示为已提交。

### 顶部阶段

`prepare → compile → draft → review → extract → continuity → proposal → commit`

- 初始：`prepare/compile` 已完成，`draft` 等待。
- 生成候选：`review` 当前。
- 接受候选：`proposal` 当前。
- 提交本章：`commit` 完成。

### 右栏

- 顶部四个窄 tab：质量 / 故事 / 上下文 / 影响。
- 默认卡片只回答一个问题，不做仪表盘堆叠。
- 质量正常时显示“可继续 + 1 条建议”；阻塞时应有明确原因和恢复动作（本 Spike 用静态通过态验证层级）。
- 上下文只默认显示“已读取 4 类 / 6,438 tok”，展开后再展示具体来源。

## 验收任务

在 1440×1000 和 1280×900 完成：

1. 从已有作品进入当前章。
2. 看清当前作品/章节/故事上下文，不离开写作面。
3. 输入 AI 写作要求并生成候选。
4. 确认候选出现但正文未变。
5. 查看“AI 读了什么”。
6. 接受候选，确认状态为“已接受，未提交”。
7. 提交本章，确认状态为“已提交”。
8. 打开“全部能力”，确认全局功能可达但不常驻干扰。
9. 保存/刷新后正文与提交状态可恢复。

## 非目标

- 不接真实 API。
- 不重构生产 `WorkbenchView`。
- 不删除旧 A/B/C 原型。
- 不证明最终视觉设计完成。
- 不增加依赖。
