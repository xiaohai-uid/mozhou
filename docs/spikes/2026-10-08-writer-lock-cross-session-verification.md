# 写锁跨登录会话互斥：验证程序（议题 #100，2026-10-08）

## 1. 待验证的主张

`apps/web/server/platform/writerLock.ts:13-16` 声明：

> 多 Windows 会话：`\\.\pipe\` 是**会话本地**命名空间，因此跨会话（不同登录会话同时跑服务）不在支持范围内。

拆开看，这句话里混了两种东西：

| 成分 | 性质 | 是否被证据背书 |
|---|---|---|
| 「命名管道默认按登录会话隔离」 | **Windows 语义陈述** | 平台事实，本仓未实测 |
| 「跨会话不在支持范围」 | **设计范围声明** | 合理（保守），但依据是上面的语义陈述而非实测 |
| 「两个独立进程争抢同一书根互斥」 | **本仓实测** | **已背书**：LOCK-01，先占后争 / 释放后恢复 / 同时争抢三阶段，连跑 3 次 PASS（`scripts/verify-cross-session-writer-lock.mjs`） |

关键区别：**「两个独立进程」≠「两个不同登录会话」**。前者在同一会话内，后者才是这句话真正涉及的情形，而后者**未实测**。

## 2. 为什么不能自动化

构造第二个登录会话需要在本机另开一个会话（RDP 第二会话 / 控制台切换 / 以另一账号运行的计划任务），属**只有人能做**的步骤。自动化只能在同一登录会话内起多个进程——那正是 LOCK-01 已经覆盖的东西，再跑一遍不增加证据。

## 3. 人工验证步骤（可复现）

前置：同一台 Windows，两个登录会话（A = 当前会话；B = 另一账号登录或 RDP 第二会话）；一个隔离书根 `<BOOK>`（临时目录 + 最小书籍布局）。

1. **会话 A 长期持锁**：需要一个「持有者」入口（现有 `scripts/verify-cross-session-writer-lock.mjs` 只跑争抢序列，**没有 --hold 模式**，需先补一个最小持有者——或临时用 `node --experimental-strip-types` 直接 import `withBookWriteLock` 起一个长驻进程）。**该持有者尚未实现**，属本程序执行前的前置工作。
2. **会话 B 尝试同一 `<BOOK>`**：跑争抢脚本，记录：
   - 会话 B 的退出码与错误码（`EADDRINUSE`？还是成功拿到锁？）；
   - 两侧实际使用的管道名（应为 `\\.\pipe\mozhou-writer-<hash>`，且逐字相同）；
   - 两个会话的账号名（**不含任何凭据**）。
3. **判定**：
   - B 得 `EADDRINUSE` ⇒ 跨会话互斥**成立**。此时 `writerLock.ts` 的「不在支持范围」应改写成**保守声明**，理由改为「未验证 + 未纳入验收」，而不是「命名空间隔离」。
   - B 绑定成功 ⇒ 互斥**不成立**，须升级为**缺陷**：跨会话同时写入同一书根会绕过写锁（作者数据损坏风险），按工作流开缺陷议题并修。
4. **记录**：两次运行的完整输出、管道名、账号名追加到本文件；结论同步进 `writerLock.ts` 注释或 ADR。

## 4. 现状结论（2026-10-08）

- 上述人工步骤**未执行**（本机未构造第二登录会话，持有者入口亦未实现）。因此本维度**明确记为「未验证」**，不得当作「已验证不支持」。
- 发布说明已按 `docs/plans/2026-10-03-gitnexus-plan-mozhou-architecture-release.md:188` 的要求写明该支持范围（见 `.github/workflows/release.yml` 的 release body 与安装器 `使用说明.txt`）。
- 未验证项的登记方式：`writerLock.ts:13-16` 的注释已同步精确化，避免读者把「平台语义」读成「本仓实测」。
