# 作者工作流能力补齐（对标 OpenWrite v1.2.2）

> 本地规格文档（Local Spec Doc）。承载规格与决策，**不是执行状态**；执行状态一律看 GitHub 议题。
> 本文件按 `/to-spec` 产出：只做综合，不做访谈。后续由 `/to-tickets` 切成纵切并发布为议题。
> 术语以 [`GLOSSARY.md`](../../GLOSSARY.md) 为准。

## Problem Statement

作者的 AI 只能按墨舟预设的管线产出，不能像作者本人那样操作项目。作者想问「我的大纲文件里第三章写了什么」，AI 读不到；想让 AI 按某个写作技能办事，技能无处安放；需要一句背景资料，AI 不能联网查。作者手上已有的 Word 稿子也进不来——建书只能从空白或一段初始正文开始。删掉一个文件就没了，没有回收站。换一台机器继续写，只能手工导出再导入。

结果是：墨舟在写作质量、版本历史与一致性上比同类产品强，但**作者的日常动作接不上 AI**，且项目数据不能在机器之间安全移动。

## Solution

给墨舟补上六条能力线，让 AI 成为「能操作项目文件的智能体」，并让项目数据可撤销、可移动：

1. **智能体工具层**：一套统一接口的工具集与注册表，AI 可读写书章文件、按需加载技能、联网检索、向作者提问。
2. **技能系统**：以 `SKILL.md` 约定存放可写盘的技能，系统提示只注入技能名与描述，正文按需取。
3. **模型循环接线**：把工具清单下发给模型、处理工具调用、执行后回填，形成可用的智能体循环。
4. **既有稿导入**：把作者已有的 txt / md / docx 稿子导入成书章。
5. **回收站**：删除改为移入隔离区，可恢复、可彻底删除。
6. **云同步与局域网同步**：WebDAV 对接公网网盘；局域网走本地通道配对。

## User Stories

### 智能体工具层

1. 作为作者，我想让 AI 读取书根内的任意文件，这样我不必把内容复制粘贴进对话。
2. 作为作者，我想让 AI 列出目录看结构，这样我能确认它看的是哪一章。
3. 作为作者，我想让 AI 在书根内新建或覆盖文件，这样它能替我整理设定稿。
4. 作为作者，我想让 AI 读取书根**之外**的文件时先问我，这样它不会翻到我别处的私人文件。
5. 作为作者，我想让 AI 碰不到系统目录，这样它不会误改系统文件。
6. 作为作者，我想让 AI 删除文件时进回收站，这样我随时能找回来。
7. 作为作者，我想让 AI 重命名与复制文件，这样整理稿件不必我手动做。
8. 作为作者，我想让 AI 在需要我拿主意时直接问我，而不是替我决定。
9. 作为作者，我想知道 AI 到底能调用哪些工具，这样我能判断它的边界。
10. 作为作者，我想让联网检索默认关闭、由我开启，这样它不会在我不知情时联网。

### 技能系统

11. 作为作者，我想把一套写作方法存成一个技能，这样下次不必重新解释。
12. 作为作者，我想让技能只由名称与描述参与提示，正文按需取，这样长技能不挤占上下文。
13. 作为作者，我想给技能附上脚本、资料与素材三类资源，这样技能能带上自己的材料。
14. 作为作者，我想让 AI 帮我新建与更新技能，这样我能用对话攒出自己的方法库。
15. 作为作者，我想让技能里的脚本**只被存放、不被执行**，这样导入别人的技能不会变成提权入口。
16. 作为作者，我想让技能标识用英文小写连字符，这样跨平台不会出路径编码问题。
17. 作为作者，我想让缺少描述的技能被拒绝，这样触发关键词不会缺位。

### 模型循环接线

18. 作为作者，我想让 AI 在对话中真正调用这些工具，这样能力才不是摆设。
19. 作为作者，我想在一次提问里让 AI 连续用多个工具，这样它能自己把事情办完。
20. 作为作者，我想看到 AI 用了哪个工具、传了什么参数，这样我能核对它的判断。
21. 作为作者，我想让工具执行失败时如实告诉我，而不是编一个结果继续。
22. 作为作者，我想让联网检索未开启时工具明确报不可用，而不是静默降级。
23. 作为作者，我想让工具调用有次数上限，这样一次提问不会失控。

### 既有稿导入

24. 作为作者，我想把一份 txt 稿导入成书章，这样我不必重新打字。
25. 作为作者，我想把一份 md 稿导入成书章，这样标题层级能自动分章。
26. 作为作者，我想把一份 Word 稿导入成书章，这样多年的存货能直接搬进来。
27. 作为作者，我想让导入时按我的选择分章（按标题、按空行、按字数），这样结果符合我的稿子结构。
28. 作为作者，我想在导入前看到分章预览，这样我能确认切得对不对。
29. 作为作者，我想让导入失败时不留半本书，这样我不用手工清理。
30. 作为作者，我想让导入的书章与手写的完全一致（草稿、基线、身份都对），这样后续流程照常走。
31. 作为作者，我想让 docx 解析零新增依赖，这样安装包不变大。

### 回收站

32. 作为作者，我想让删除的稿件进回收站，这样误删能撤回。
33. 作为作者，我想在回收站里看到原始路径与删除时间，这样我能认出是哪一份。
34. 作为作者，我想恢复时若原路径已被占用就拒绝并告诉我，这样不会覆盖新内容。
35. 作为作者，我想能彻底删除回收站里的条目，这样我能真正清掉不要的东西。
36. 作为作者，我想让回收站条目不会被伪造的标识串到别处，这样隔离区边界可靠。

### 云同步与局域网同步

37. 作为作者，我想用 WebDAV 把书稿同步到网盘，这样我不必自建后端。
38. 作为作者，我想在同步前看到哪些文件会变，这样我能确认范围。
39. 作为作者，我想在冲突时保留双方并让我选，这样不会静默丢稿。
40. 作为作者，我想让同步只走 http/https 且拒绝内网与保留地址，这样不会被诱导去请求内网服务。
41. 作为作者，我想在手机上通过局域网配对连上桌面端，这样出门也能接着写。
42. 作为作者，我想让局域网通道有配对凭据，这样同一网络里的别人连不上。
43. 作为作者，我想让同步中断后能续上，这样长稿不必重传。
44. 作为作者，我想让同步不删本地没同步过的内容，这样同步失败不会造成丢失。

## Implementation Decisions

### 分层与职责

- **工具层与传输分离**：工具只做参数校验、授权与结果整形，**自己不触网、不执行命令**。联网检索由宿主注入既有带出站防护的实现；提问由宿主注入回调。这样工具层不会成为绕过出站防护或提权的旁路。
- **路径权限三档**：书根与技能根内直读直写；两者之外需作者确认；系统目录直接拒绝。判定集中在单一模块，工具一律经过它，不各自实现。
- **不提供命令执行工具**：任意命令执行是提权面，且与「技能只存不执行」的边界冲突。需要跑脚本时由作者自己动手。
- **技能是可写盘的数据，不是可执行体**：`scripts/` 按文本资源存放，本仓从不执行其中内容。这一条同时是安全边界与迁移边界。
- **按需加载**：系统提示只注入技能名与描述；正文与资源由工具现取。这是控制上下文占用的关键。
- **删除一律软删除**：文件删除动作走回收站，不直接抹掉内容。「AI 能删文件」不等于「内容会丢」。
- **回收站条目标识**：时间戳 + 密码学随机后缀；标识解析按白名单字符校验后再拼路径，**不得用会脱离根目录的路径解析**（这是隔离区边界的硬要求）。
- **导入零新增依赖**：docx 是 OOXML 压缩包，用 Node 内置解压读取正文 XML，不引入三方 zip 库。
- **同步的出站边界**：WebDAV 目标只允许 http/https，并在发请求前校验主机、拒绝环回与私有及保留地址。局域网通道是**入站监听 + 配对**，不是对任意 URL 的出站请求，故按相反方向校验：只接受同网段对端。

### 模块与接口

- 工具层：一个工具基类（名称 / 描述 / 参数 schema / 执行）、一套具体工具、一个注册表（注册 / 开关 / 下发定义 / 按名分发）。参数与结果都是结构化对象。
- 技能存储：解析与渲染 `SKILL.md`（frontmatter + 正文）、按标识读写、三类资源计数、列出摘要（**不含正文**）。
- 回收站存储：移入、列出、恢复、彻底删除；恢复时原路径被占用即拒绝。
- 导入器：按格式解析出「章标题 + 正文」序列，再交给既有建章路径写入。
- 同步：清单比对、增量传输、冲突保留双方、断点续传。
- 模型循环：工具定义随请求下发；解析流式返回中的工具调用；执行后把结果回填并继续，直至模型不再调用工具或达到次数上限。

### 与既有契约的关系

- 导入写回必须走既有书章写入路径与身份纪律，不得自建一套槽位。
- 工具层的文件写入不得绕过既有正文写入契约：正文仍是纯文本，结构投影仍走既有键。
- 同步只搬运既有数据形态，不引入第二套真相源。

## Testing Decisions

缝由作者确认为**两层都要**：

- **模块层（保行为）**：工具层、技能存储、回收站存储、导入解析器各自按外部行为测。既有先例是 `server/agent` 与 `server/recycle` 下的行为测试。好的测试只断言可观察行为与副作用（写了什么、拒了什么、回读是否一致），不断言实现细节。
- **路由层（保装配与授权）**：通过 HTTP 边界测工具下发、执行分发、技能增删改查、导入、回收站操作。既有先例是各 `*Routes.test.ts` 的路由测试台架。这一层负责证明「装配起来了」与「未授权路径被拒绝」。

补充判定：

- 路径权限必须有负例：越界、系统目录、空字节、无书根相对路径各自给出预期的拒绝或确认。
- 回收站必须有「原路径被占用时拒绝覆盖」的负例。
- 同步的出站校验必须有负例：非 http(s)、环回、私有地址各被拒绝。
- 导入必须有「失败不留半本书」的负例。
- 模型循环必须有「工具失败不编结果」「次数上限生效」的负例。

## Out of Scope

- **命令执行工具**：有意不做，理由见实现决策。
- **复制对方受版权内容**：提示词原文、界面文案、示例文本、资源文件一律不复用；只参考分层与协议设计。
- **会员与卡密链路**：不在本次范围。
- **Electron 桌面迁移**：另有规格（迁移审计的 E01–E09），本规格不重复。

## Further Notes

- **能力对照的结论**：墨舟在写作质量、版本历史（章节历史 / 差异 / 恢复 / 备份）、一致性对账与导出格式上强于对标对象；本规格补的是对标的强项，不是补齐短板。
- **本规格与「技能市场」的关系**：既有 `skills/catalog.ts` 是内置的纯数据提示词配方，不可写盘、明确禁止执行；本规格的技能存储是可写盘的技能目录。两者形态不同、职责不重叠，故并存。
- **规格落点**：本文件放在 `docs/specs/`（与既有 `browser-data-migration-format-v1.md` 同处）。术语权威把「本地规格文档」描述为 `.scratch/<feature-slug>/` 之下，此处按作者选择与议题追踪文档「规格落 `docs/`」那条放置，两处口径差异在此显式记录，不静默引入。
- **发布方式**：本文件是规格，**不创建 GitHub 议题**。执行状态在 `/to-tickets` 阶段以议题形式发布，并打 `ready-for-agent` 状态标签。
- **前置事实**：工具层与回收站存储的一部分已按本规格的决策先行落地并通过行为测试；本规格写定后，未落地的部分按纵切切分推进。
