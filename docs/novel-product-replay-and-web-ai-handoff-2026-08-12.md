# 墨舟小说产品全面复盘与网页端 AI 交接报告

日期：2026-08-12  
范围：Obsidian 中全部与小说产品、OpenWrite 逆向、灵笔、零界道种、墨舟写作工作流相关的资料；墨舟当前代码；用户提供的生产截图。  
用途：交给无法访问本地环境的网页端 AI，继续制定并执行墨舟“新作品创建后立即开始写作”的修复计划。

## 1. 最终结论

用户在生产环境创建新作品后看到人物库 0 条、世界观 0 条、章节 0 章、RAG 注入配置和审查/导出模块，找不到下一步写作入口。这个状态作为“作品管理后台的资料空态”可以成立，但作为“创建作品后的首次写作流程”不合理。

根因不是数据库不能创建，也不是 RAG 必须先配置，而是：

1. `POST /api/v1/novels` 只创建作品记录；
2. 前端 `ProjectsView.createBook()` 创建成功后只刷新作品列表、选中作品并加载空详情；
3. 首章仍隐藏在右侧“章节”卡片的加号里，用户需要额外点击、输入标题；
4. 创建完成后没有“开始写作”主动作，也没有跳转章节编辑器；
5. 空章节的“章节起笔”能力已经存在，但没有接入“新作品创建”这条入口链。

因此，当前 P0 是“作品创建 → 首章编辑器”的激活/首写路径断裂，而不是再增加人物库、世界观、RAG、审查或导出功能。

推荐产品契约：

```text
创建作品（只需书名）
  → 自动准备“第一章”空章节
  → 直接进入章节编辑器
  → 用户可选择自己先写，或让 AI 章节起笔
  → AI 输出先作为候选
  → 用户确认后插入正文
  → 人物/世界观/风格/RAG 在写作过程中逐步补充，全部可选
```

不能要求作者在真正开始写作前，先完成资料管理工作。

## 3. 当前代码事实

### 3.1 作品创建

文件：`app/components/features/projects-view.tsx`

`createBook()` 当前逻辑：

```text
校验书名
→ POST /api/v1/novels { name }
→ 清空输入
→ refreshList()
→ setActiveId(novel.id)
→ loadDetail(novel.id)
```

没有创建章节、没有跳转、没有“开始写作”按钮。

作品详情页当前三栏顺序是：

```text
人物库 | 世界观设定 | 章节
RAG 注入配置
审查记录
导出与备份
```

章节空态文字是“还没有章节，点击右上角新建”，这把关键动作降成了卡片内的次要图标。

### 3.2 API 与数据模型

文件：

- `app/app/api/v1/novels/route.ts`
- `app/app/api/v1/novels/[id]/chapters/route.ts`
- `app/lib/novels/service.ts`
- `app/lib/schema.ts`

现有能力已经足够支撑最小首写闭环：

- `POST /api/v1/novels`：只要求 `name`，可选 `description`；
- `POST /api/v1/novels/:id/chapters`：创建章节，标题必填，自动编号；
- 新章节正文 `content` 初始为空；
- `GET /api/v1/novels/:id/chapters?chapterId=X`：读取章节正文；
- `PATCH /api/v1/novels/:id/chapters?chapterId=X`：保存正文；
- `POST /api/v1/novels/:id/chapters/chat?chapterId=X`：章节内流式 AI 对话；
- 空正文会选择内置“章节起笔”技能；
- AI 回复先进入章节消息，用户确认后才通过插入接口写入正文；
- 已有 Undo/Redo、选区替换、乐观并发冲突保护。

### 3.3 章节编辑器事实

文件：`app/components/features/chapter-editor-view.tsx`

已存在的空章节行为：

- 空正文时默认场景技能为“章节起笔”；
- 输入区提示“空章节：让 AI 起笔，再逐轮调整”；
- 页面内已有“让 AI 起笔这一章（技能：章节起笔）”按钮；
- 生成结果可以“插入正文”；
- 生成期间支持停止；
- 插入后已有 Undo/Redo 和冲突保护。

这说明本轮不需要重新设计 AI 章节编辑器，首先要把新作品创建成功后的导航接到这条已有能力上。

### 3.4 工作台事实

文件：`app/app/workspace/page.tsx`

当前“还没有作品”空态的按钮是“创建作品”，跳转 `/projects`。这个入口可以保留，但 `/projects` 创建完成后的下一步必须变成写作，而不是继续停留在空的资料管理页。

```text
  → WRITING_EDITOR
  → CANDIDATE_GENERATED
  → USER_ACCEPTED_OR_REJECTED
  → WRITING_EDITOR
```

可选的 `SETUP_CANON`、`CHOOSE_STYLE`、`ENABLE_RAG` 都不能阻塞 `FIRST_CHAPTER_READY`。

### 6.2 推荐黄金路径

```text
工作台“创建第一部作品”
  → 输入书名（可选简介/题材，不能强制）
  → 创建作品
  → 准备第一章（默认标题“第一章”，允许立即改名）
  → 进入章节编辑器
  → 页面明确给出：
      A. 我自己先写
      B. 让 AI 起笔
  → AI 生成候选
  → 用户确认后插入正文
```

如果仍保留作品管理页，作品管理页应显示“开始写作”主按钮；人物、世界观、风格、RAG 应作为“完善作品”次级任务。

### 6.3 首写规则

- 只输入书名就可以开始；
- 不要求先创建人物；
- 不要求先创建世界观；
- 不要求先配置 RAG；
- 不要求先安装 Skill；
- 不要求先配置风格；
- 不生成假人物、假世界观或假章节摘要来填空；
- 空章节有明确的“章节起笔”场景技能；
- AI 生成内容先成为候选，用户点击确认后才写入正文；
- 用户可以绕过 AI，直接在编辑器写第一段；
- 创建失败或第二步失败时必须提供可恢复的重试路径，不能留下“创建成功但无法继续”的死状态。

### 6.4 新作品激活方案的实现取舍

推荐网页端 AI 优先评估以下最小实现：

1. 前端创建作品成功后创建默认第一章，并直接导航章节编辑器；或
2. 增加一个受归属校验保护的“创建作品并准备第一章”服务端事务，避免两次请求中间留下半成品；
3. 保留“只创建作品”作为次级路径，仅在用户明确需要先整理资料时使用；
4. 复用已有章节编辑器和章节起笔能力，不另建一套首章页面；
5. 如果采用两次请求，必须覆盖第二步失败的重试/恢复状态；如果采用事务，必须覆盖重复点击和并发创建。

## 7. 实现范围建议

### P0：新作品到首章编辑器

- 修改 `ProjectsView` 的创建成功行为；
- 增加“开始写作”主按钮和可见的首章空态；
- 让第一章创建结果携带 `chapterId` 并导航 `/chapter/:chapterId?novelId=:novelId`；
- 首章标题默认为“第一章”，但可在编辑器修改；
- 复用现有空章节“章节起笔”按钮和普通编辑器；
- 保留作品资料页作为后续管理页。

### P0 测试

必须使用能观察真实 consumer 行为的测试，不只测 mock 函数被调用：

- 作品创建成功后确实存在一条草稿第一章；
- 导航目标确实是该作品的章节编辑器；
- 空章节 UI 有“我自己先写”和“让 AI 起笔”两条可达路径；
- AI 起笔请求的最后一条 user message 是当前请求；
- 章节起笔技能、身份基座、作品归属和章节上下文都进入最终 provider payload；
- AI 候选未确认前不会修改 `chapters.content`；
- 点击插入后正文更新，Undo 能恢复；
- 新建失败、章节准备失败、重复点击和刷新恢复都有确定行为；
- 已有作品和已有章节的写作链不回归；
- 不把测试通过数当成 payload 正确的替代证据。

### P1：渐进式作品引导

在 P0 首写闭环稳定后，才考虑：

- 可选的题材/一句话设定/风格引导；
- AI 帮作者生成角色、世界观、大纲候选；
- 每份资料用户确认后再入库；
- 用“完善作品”任务清单提示下一步，而不是把空卡片当作错误；
- 章节完成后生成摘要并进入 RAG/上下文；
- 真实使用反馈驱动后续功能优先级。

### 本轮明确不做

- 不重做整个应用 UI；
- 不把 RAG、人物、世界观改成强制 onboarding；
- 不自动填充演示数据；
- 不引入 OpenWrite 的终端工具；
- 不引入多 Agent 或复杂工具调用运行时；
- 不做新的富文本编辑器迁移；
- 不做会员/支付/跨设备会话/HTML 书源解析器/版本历史；
- 不因为这个 UX 问题重新改生产部署平台。

## 8. 网页端 AI 必须交付的内容

请网页端 AI 以本报告为事实基线，继续之前的审阅/计划流程，按以下顺序输出：

1. 对“新作品创建后的首写路径”给出明确的产品判断；
