# 墨舟小说项目与四个参考项目的生产化路线研究

日期：2026-08-16

## 目的

这份记录用于和网页端 AI 讨论墨舟的小说生产工具路线。墨舟不是小红书项目，也不是视频生产项目。目标是先验证小说作者是否愿意持续使用，再决定是否把它做成商用下载型产品。

- 用户希望官网后续主要承担品牌展示、软件下载、付费、账号/授权和更新，不承担主要小说创作工作，原因是长时间生成和大文本处理放在官网上会带来流量与推理成本。
- 真正的写作工作台应优先考虑本地客户端、桌面端或本地服务配合网页界面。云端保留支付、授权、更新、可选同步/备份等轻量能力。

## DeterminFlow 的实际价值

它解决的是“模型不确定，但生产流程必须确定”的问题。每个任务冻结工作流定义、输入和节点快照；Agent、脚本、审批和子流程是不同节点；结构化输出需要校验、修复或重试；节点有检查点、尝试记录、token 账本和审计历史；进程重启后可以从恢复点继续。

值得带入墨舟：

- `generation_plan`、`run`、`step`、`attempt`、`checkpoint` 的分层；
- 每个步骤的输入、输出、状态、错误和重试记录；
- 失败时可以重试或跳过，而不是页面一直转圈；
- 任务执行时使用冻结的定义快照，避免中途改配置导致结果不可解释；
- 把模型输出验证、数据库写入、文件操作等确定性动作与 Agent 推理分开；
- 成本和 token 按任务、步骤、尝试记录。

不应照搬：

- 它的通用工作流编辑器和复杂插件宿主不是墨舟第一阶段的用户价值；
- 插件与 Core 同进程、同权限，页面也不是安全沙箱，不能直接当成商用扩展安全模型；
- 仓库声称的小说插件 token 节省比例只能当作项目方自己的报告，不能当成墨舟已验证的商业结论。

许可证边界：AGPL-3.0。商业产品不能未经审查就把其代码直接嵌入、修改后分发或混入闭源客户端，应先做许可证合规评估。仅借鉴抽象思想与自行实现也要避免复制具体代码和受保护资产。

## ArcReel 的实际价值

它本质上是一个自部署的视频生产工作区，不是小说写作系统，但它把长时间异步生产做得很清楚。代码结构里可以看到 workflow plan/state、episode ledger、artifact provenance、generation tasks、resume executor、project events、SSE channel、provider adapter 和 usage/cost estimation。

值得带入墨舟：

- 生成不能只有“开始/结束”，应该有持久化的任务状态和事件日志；
- 前端应能看到当前阶段、已完成步骤、下一步、预计等待原因、失败原因和可执行操作；
- 浏览器刷新、客户端重启、网络暂时断开后可以恢复任务状态；
- 每个候选文本、摘要、审查报告和正式章节都要有来源、版本、生成任务和当前性记录；
- 不同模型供应商应通过统一适配层接入，并记录消耗与估算成本；
- SSE 或本地事件总线只负责传递状态，真实状态要持久化，不能靠内存消息维持。

不应照搬：

- 它的角色/场景/道具/分镜/视频/剪映草稿等领域模型与小说不同；
- 不要把视频资产生成的复杂度移植成墨舟的首版小说流程；
- AGPL-3.0 同样是商业集成的法律边界。

## InkOS 的实际价值

这是四个项目里最接近小说生产本体的一个。它把小说写作拆成 `plan -> compose -> write/draft -> audit -> revise -> state sync`，并用 Planner、Composer、Writer、Observer、Reflector/Settler、Auditor、Reviser 等角色分担工作。

关键做法：

- 结构化 JSON 是故事状态的权威来源；Markdown 是人可读投影；SQLite 用于记忆检索；
- 任务开始前生成当前章节的 intent、context、rule stack、trace 等运行时产物；
- 不把全部历史文件粗暴塞进 prompt，而是按任务编译需要的上下文；
- 写完后提取事实和状态变更，使用结构化 delta、schema 校验和不可变更新；
- 章节审查和修订可以自动循环，也允许严格、宽松、始终修订等策略；
- 长任务在后台运行，用户可以继续聊天、取消、重试；刷新或重启后恢复真实状态；
- 写入有锁、冲突状态、备份和回滚，完成态只来自真实工具和文件结果；
- CLI、TUI 和 Studio 共用同一套动作面。

值得带入墨舟：

- 小说工作台必须有正式的故事 Canon、章节意图、摘要、伏笔和人物状态，而不能只靠三张设置表；
- 每次生成都应该有“本次使用了什么上下文、遵循什么规则、产生了什么候选、哪些状态变化待确认”的证据；
- 讨论、计划、写作、审查、修订需要不同动作入口，不应都伪装成一个聊天框；
- 长生成时用户可以继续做别的工作，完成后再查看和确认；
- 作品数据必须能够导出、备份、恢复和回滚。

不应照搬：

- InkOS 是 AGPL-3.0，不能把代码直接塞进闭源商业客户端；
- 它当前能力面很大，墨舟不应一次性复制所有互动影游、翻译、开放世界和多语言能力；
- CLI/本地文件优先的架构需要重新适配墨舟的安装、授权和 UI 体验。

## oh-story-claudecode 的实际价值

它更像一个高质量的小说技能和本地工作流包，而不是后端生产运行时。它覆盖长短篇写作、长短篇拆文、扫榜、导入旧稿、去 AI 味、审查、封面和本地 dashboard，并通过 story-setup 给 Claude Code、OpenCode、ZCode、Codex 等环境部署技能、hooks、agents 和参考资料。

值得带入墨舟：

- 小说领域的实际工作方法和阶段拆分；
- 长篇写作需要大纲、角色、世界观、追踪、章节摘要和逐章验收；
- 导入既有小说时，要把正文反向整理为可续写的作品状态；
- 生成后要做字数、句式、AI 痕迹、连续性和细纲覆盖等确定性检查；
- 技能应按需加载，不能每次把几十 KB 的全部规则塞给模型；
- 本地 dashboard 只监听 127.0.0.1，并对路径、文件扩展名、文件大小、并发版本做安全限制。

不应照搬：

- 它的核心是本地 Agent/CLI 技能，不是 SaaS 后端；
- hooks、custom agents 和不同 CLI 的适配能力依赖具体运行时，迁移到墨舟网页或桌面端必须逐项验收；
- MIT 许可证较宽松，但仓库里的参考资料、图片和第三方依赖仍需逐项确认许可证。

## 墨舟当前事实和已知问题

### 已经完成或有工程证据的部分

- 已上线生产网址，当前代码是 Next.js、TypeScript、Tailwind/shadcn，PostgreSQL/pgvector，one-api 网关。
- 独立对话和章节对话的上下文 P0 修复已经落地：base identity、消息边界、压缩历史注入、章节正文参考隔离、payload observer、owner scope 校验。
- 章节编辑器已经有正文保存、章节对话 SSE、候选回复、插入正文、选区替换、冲突提示、Undo/Redo 和自动保存等链路。
- 最近工程门禁有 20 个测试文件、175/175 测试通过，生产构建通过。
- 这些证据证明已实现代码切片的回归，不等于产品商用验证，也不等于所有 UI 承诺都接了真实后端。

### 首次写作和产品可信度问题

- 新建作品目前只创建作品记录，不自动创建第一章、不返回首写状态、不自动进入编辑器。新用户看到人物 0、世界观 0、章节 0，不知道下一步。
- 创建作品和创建第一章是两个独立请求，存在部分成功、重复点击、并发章节号和失败后无法恢复风险。
- 当前生成可能等待较久，但如果没有真实的阶段反馈，用户会认为系统失效；这不仅是 UI 问题，也是任务状态、事件、取消、重试、恢复没有形成完整协议的问题。
- 生成结果必须先成为候选，用户确认后才写入正文；不能让模型直接覆盖正文。
- 页面和源码仍有 Mock Preview、写死审查记录、禁用的导出/备份/同步卡片等状态漂移或未开放能力，必须明确真实能力和示意能力。

### 领域模型和生产闭环问题

- 当前 schema 主要是 novel、chapter、character、worldview、style、skill、chat message 和 usage，缺少正式运行时真源：作品简报、卷纲/章纲/细纲、摘要、地点/物品/事件/关系、伏笔/故事线、导入资料、审查任务/报告、后台任务、恢复点、候选变更记录、导出包版本。
- 现有 RAG 主要是人物/世界观关键词检索和正文末尾固定长度参考，还不是可验证的按任务上下文编译器。
- 技能目前更接近名称加 systemPrompt 的注入，不是有依赖、权限、工具、输入/输出契约、运行记录和产物的真实执行单元。
- 拆文、扫榜、抽卡、封面、Agent 目前有部分页面或 API，但没有全部形成可恢复、可审查、可写入、可导出的完整闭环。
- WebDAV/同步、导出、备份、联网源、榜单解析、密码加密、正文大小限制、生产限流和滥用保护仍需补齐或明确限制。
- 用户隔离、RAG 归属、外部资料权限、备份恢复和生产数据库演练要以真实验收为准，不能只看单元测试。

### 已有验证方案的边界

目前已经做过一个本地、非生产的 synthetic-user runner 原型，模拟正常反馈、无反馈、以及等待时的刷新/重试/离开等行为。它只能生成假设和回归信号，不能代替真人。

此前讨论得出的正确验证方向是：

- 合成用户关注状态理解、等待价值感、主动继续操作、取消/重试/刷新等行为；
- 用 5 到 10 名真实用户校准等待时长、反馈文字和用户是否真正继续读/改/接受/重写；
- 对比裸 LLM 与最小小说工作流壳，而不是直接做完整商业系统；
- 第一阶段 Go/No-Go 指标包括：大多数用户不把等待误判为故障、反馈能减少无意义刷新/重试、用户认为结果值得等待，并且愿意继续编辑或写下一步；
- 自动化测试和 175 个绿灯不能替代真实用户价值验证。

## 目前建议的产品路线

1. 把官网定位为下载、付费、账号/授权、更新和可选同步入口，不把主要生成计算放在官网。
2. 把本地写作工作台作为主产品：本地项目文件/SQLite/任务状态/缓存/导出，模型请求可由用户自己的 API 或可选中继承担。
3. 先只做最小小说闭环：创建作品、自动第一章、写作意图、上下文编译、流式候选、候选确认、正文原子保存、章节摘要/状态更新、失败重试/取消/恢复、导出。
4. 从 DeterminFlow 借任务/步骤/尝试/检查点/审计，从 ArcReel 借事件流/长任务/产物来源/恢复，从 InkOS 借小说 Canon/章节状态/审查修订，从 oh-story 借技能和写作方法。
5. 先做原型和真实用户验证，再决定是否迁移更多技能、做多 Agent、做复杂市场或做完整云同步。
6. 将 AGPL 项目视为架构参考或独立服务候选，商业集成前完成许可证审查；MIT 项目也要核对具体资产和第三方依赖。

## 需要网页端 AI 讨论并给出结论的问题

请基于以上完整事实，不要再把项目理解成小红书，也不要根据缺失信息自行补全。请明确区分“仓库 README/源码声称”“墨舟已有工程证据”“还没有真实用户证据”。请讨论：

1. 这四个项目分别应该放在墨舟的哪一层，哪些只借思想，哪些可以做独立进程或适配器，哪些绝不该作为首版依赖。
2. 在官网只负责下载和付费、本地工作台负责创作的前提下，推荐桌面/本地架构、授权方式、模型调用方式、可选云服务边界和数据导出策略。
3. 针对“生成时间长且没有反馈”，给出端到端状态机、事件模型、前端反馈内容、取消/重试/恢复语义和最低可验收指标。
4. 针对当前墨舟的问题，给出 P0/P1/P2 顺序，并说明哪些问题应先做原型验证，哪些可以直接工程修复。
5. 设计一个最小可行的小说生产闭环，说明第一阶段不做什么，避免一开始堆完整 Agent、技能市场和复杂同步。
6. 给出真实用户、合成用户和自动化回归如何组合，以及何时 Go、何时 No-Go。
7. 给出商业许可证和源码依赖风险的实际处理建议，但不要把法律意见说成确定结论。
