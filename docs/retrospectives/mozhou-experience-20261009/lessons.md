## L01 发布证据必须对应实际构建输入

**触发条件**：要交付构建产物（安装包、桌面壳、发布包），且工作区可能不干净，或刚经历过他人留下的未提交改动。

**失败机制**：`事实`＋`推断`——构建输入可以包含未提交代码，而记录只写 git HEAD。HEAD 标识的是一个提交，不是这次构建实际读到的文件集合。10 月 3 日发现过一次，四天后同类问题复发；散文式提醒没有进入构建入口，所以提醒没有起作用（`推断`：促成因素是"经验停留在文档、未绑定到机械检查点"）。

**具体动作与验收**

1. 记录 `sourceCommit`、`sourceCommitSha`、`dirty`、`dirtyFiles`，并让 `print-stamp` 把这些内容打印进产物元数据（HC01 已落地的做法）。
2. 验收看**产物里的戳**，不是看仓库状态描述；仓库事后干净不能补救已生成的包。
3. 已有干净产物不要为了取证覆盖它。要证明输入来源，就换一次干净重建，或对两份产物分别取证。

**例外与失效条件**：纯本地开发快照、无需他人复现的调试产物可以不写脏戳——但不能把这类包拿去交付或当验收依据。

**现有防护与缺口**：CHG-20261008-21 已加入脏工作区标记。缺口：该标记当时只在真实仓库打印通过，**未完整重建安装器**；本轮未复测。

**案例**：HC01。

## L02 下层实现存在 ≠ 路由可达

**触发条件**：给某个接口或能力写"已支持""已接入""已实现"，尤其是入口有方法闸、鉴权白名单或分支条件的时候。

**失败机制**：`事实`——两个独立案例方向相同。下载页：`事实`——浏览器发 GET query，安全层按规范把空 body 规整为 `{}`，handler 从 body 取 id，返回 400（HC14）。公开目录：`事实`——实现与策略都登记了，但入口方法闸只允许 membership 的 GET，于是 catalog GET 被拦成 404（HC15）。共同促成因素是**只验证了目标组件，没有从真实消费者走一遍**。

**具体动作与验收**

1. 从真实入口（浏览器链接、实际 HTTP 客户端、页面按钮）出发，逐段走到 handler：方法、参数通道、鉴权、白名单。
2. GET 与 POST 分开验。GET 用 URLSearchParams，POST 用 body，并对两者用同一份白名单枚举。
3. 验收看真实响应体和返回内容，不只看 HTTP 状态码。

**例外与失效条件**：仅内部调用、无 UI 入口的能力可以不查 UI 路径，但仍要确认调用方使用的通道与方法。

**现有防护与缺口**：HC14/HC15 的端点级正例、穿越与不存在场景当时通过。缺口：**浏览器点击路径与 hosted 鉴权未验**（HC14、HC15 记录）。

**案例**：HC14、HC15。

## L03 校验分散在不同数据面，就等于没有校验

**触发条件**：同一份正文或状态，存在多个独立写入通道（自动保存、流式落盘、采纳、撤销、恢复）。

**失败机制**：`事实`＋`推断`——正文层有 CAS 保护，但模型调用与操作结果层是独立的；CAS 通过不代表副作用只发生一次。`推断`促成因素是**把"正文没变"当成"操作没重复"**。

**具体动作与验收**

1. 用持久化的 `operationId` 记录同一次操作的结果，使重放可判定而不产生第二次副作用。
2. 验收必须**回读数据面而不是只看返回值**：正文、`revision`、候选池、操作状态一起看。
3. 记录线性化顺序，确认"自己成功"与"他人提交"可区分。

**例外与失效条件**：纯读取、无外部副作用的路径不需要 `operationId`。

**现有防护与缺口**：地图记载 W3 补齐。缺口：`事实`——本轮**未重新核对接口源码**，历史文档与源码链未闭合，本次未过图谱门禁（HC06）。

**案例**：HC06。

## L04 PID 存活、心跳超时、锁文件年龄都不等于所有权

**触发条件**：实现或审查进程锁、写锁、预算锁、单例守卫，尤其是需要判定"上一个主人还活着吗"的地方。

**失败机制**：`事实`——注入另一个存活 PID 后，新实例错误地拒绝启动（HC03）；预算保护器用 `mtime` 大于 30 秒强删且不验主人，导致能夺活锁或重置额度（HC11）。`推断`促成因素是**用间接信号代替身份绑定**，PID 会复用、年龄与死锁没有逻辑关系。

**具体动作与验收**

1. 绑定 `owner token` + 资源范围（数据根路径、账号）+ 会话标识，而不是用 PID 数字本身。
2. 主人进程死亡后，恢复路径必须明确：等待 `EEXIST`、验证身份、还是安全夺回。
3. 初始化与占用必须同临界区，初始化要幂等。
4. 分别验证：跨登录会话、网络共享、重入、崩溃恢复——**各自单独取证**。

**例外与失效条件**：单用户本地单进程场景可以用简化锁，但要在文档里写明不支持的场景，不要让它读起来像通用保护。

**现有防护与缺口**：HC03 的同登录会话双进程测试通过。缺口：**跨登录会话互斥未实测**，PID 复用是通过模拟注入的，不是真实复用。

**案例**：HC03、HC11、N/A（T6 回放场景）。

## L05 恢复过程本身也会中断，恢复验证必须覆盖二次中断

**触发条件**：写任何崩溃恢复逻辑，尤其是有 journal、有"回滚/重放"步骤的路径。

**失败机制**：`事实`——二次中断探针显示：恢复"成功"、journal 已删、正文标记 committed，但追踪从 930 字节/2 行变成 0（HC02）。直接原因是**"盘面已等于 base 字节数"被判定为 untouched 而未重放**。`推断`促成因素是**只验证了单次失败**，把"恢复返回成功"当作"恢复完成"。

**具体动作与验收**

1. 把"恢复自身中断"作为**独立窗口**单独测，不能复用单次成功的结论。
2. 验收要**回读正文和事件**，不只看 journal 是否删除。
3. 区分四种实验各自能证明什么：手工构造现场、进程终止、成功后重启、物理断电。三者不能互相外推。

**例外与失效条件**：无 journal 的路径（如直接原子替换）不适用本条，但其"替换中途失败"仍需要独立窗口测试。

**现有防护与缺口**：单次六阶段通过、二次中断失败。缺口：`事实`——**修复状态未知**（HC02）。

**案例**：HC02、T5 回放场景。

## L06 共用函数的覆盖 ≠ 调用方输入形状的覆盖

**触发条件**：多个模块复用同一底层函数（恢复、写盘、CAS、序列化），但各自传入不同字段与不同顺序。

**失败机制**：`事实`——保存正文复用提交恢复函数，但保存用的 journal 字段与提交不同，既有恢复测试（REC-01~04）**不能直接覆盖保存路径的输入形状**（HC19）。`推断`促成因素是**用"共用函数已测"推断"所有调用方已测"**。

**具体动作与验收**

1. 按**该调用方实际使用的字段和真实写盘顺序**构造测试输入，不用通用 fixture。
2. 验收前先做负例：确认这个测试在缺少该字段时**会失败**（否则它什么都没测）。
3. 检查是否存在测试根本没覆盖的窗口，例如进程被杀（onStage kill）而非仅异常注入。

**例外与失效条件**：字段与顺序完全一致的两个调用方可以共用测试，需在记录里写明这一等价性。

**现有防护与缺口**：2/2 正例、2/2 空操作负例、43 项恢复回归通过。缺口：**未做 onStage kill**（HC19）。

**案例**：HC19、N02。

## L07 副作用完成后没有回收；取消语义必须区分三层

**触发条件**：任何 `await` 写文件、调用上游模型、启动子进程之后可能被取消、超时、切章打断的流程。

**失败机制**：`事实`——写盘前检查取消信号，`await writeFile` 期间取消后报告已经留在磁盘上；双定时器还会把 Timeout 与 Cancelled 错分（HC08）。`推断`促成因素是**生命周期被重复管理**（两个定时器各管一段），以及**只测了调用前取消**。

**具体动作与验收**

1. 阻塞写盘，制造"取消发生在副作用进行中"的窗口；分别测取消、超时、切章。
2. 验收要回读**落盘文件、活动章节、revision、报告关联、候选池**——不只断言取消返回值正确。
3. 明确区分三种不同的保证：**下游结果被丢弃** ≠ **资源被回收** ≠ **上游任务真的停止**。三者要分别取证。
4. 副作用结束后**重新核对身份与取消状态**，不依赖进入时的判断。

**例外与失效条件**：无副作用的纯计算路径不需要本条。

**现有防护与缺口**：历史文档记载修复闭环（HC08）。缺口：**真实付费上游的停止行为未验证**。

**案例**：HC08、HC07（成功反例）。

## L08 构建/测试通过、CI 全绿，都不覆盖缺失的门

**触发条件**：本地检查全绿后准备宣称"满足交付要求"；或本地封装脚本与 CI workflow 并行演进。

**失败机制**：`事实`＋`推断`。本地 wrapper 只跑 build/test/graph，用 `act` 跑真实 workflow 时发现 **167 个 lint 错误**；修完一次之后，新编排的阶段 4 又漏了同一个门（HC16）。`事实`图谱侧同理：CI 全绿时 HEAD 存在环，madge 解析出 2030 条边但**跨包边为 0**（HC17）。`推断`促成因素是**"本地绿"被当成"CI 绿"的替代品**，以及**只修旧入口、不枚举新编排器**。

**具体动作与验收**

1. 从**实际 workflow 文件**逐项对账本地编排，列出差异清单；不要信任本地封装脚本自己声明的覆盖范围。
2. lint 与依赖审计是独立门，不能被 build/test 通过覆盖。
3. 检测工具本身要有**正反例自检**：相对环与跨包环各至少一条合成反例，确认检测器真的会报。
4. 未运行的检查写成"未运行"，不写成"通过"。

**例外与失效条件**：本地确实覆盖了 workflow 全部任务且命令、环境一致时，可以只做命令一致性核对——但要说清是哪一份 workflow 文件、哪个提交。

**现有防护与缺口**：167→0 修复完成，后续门通过。缺口：**hosted 环境、动态 import 未验证**（HC17）。

**案例**：HC16、HC17。

## L09 存在不等于可用；枚举共享消费者，不只测直接调用方

**触发条件**：替换共享控件/共享函数/共享契约，尤其是被多个界面或模块引用的类型。

**失败机制**：`事实`——替换 TipTap 共享控件时，首轮全量测试**遗漏了共享消费方 DialogueStream** 的同等测试；补了 DOM 断言才通过（HC05/N05）。`推断`促成因素是**只测直接调用方**。

**具体动作与验收**

1. 从共享符号**枚举全部消费者**，逐一确认它们有对应测试。
2. 涉及 UI 时补 DOM 断言与浏览器边界测试，不能只跑单元测试。
3. 图谱缺失、接线未确认时，写明"未接线"而不是用合成项目通过来代替。

**例外与失效条件**：仅内部使用、无 UI 消费者的工具函数可只测直接调用方，需在记录里写明。

**现有防护与缺口**：2084 项通过后补测通过。缺口：**IME、浏览器、Redo 仍未验证**（N05）。

**案例**：N05、N02。

## L10 先信规范表、不核消费者，会制造新的分歧

**触发条件**：按术语表/规范/ADR 批量清扫代码、文档、文案。

**失败机制**：`事实`——GLOSSARY 自身矛盾；清扫后"上下文收据"的 4 处全部是上一轮自己引入的（HC18）；中文子串扫描**误报**了 TypeScript 守卫与门禁（"禁"命中"门禁"）。代码长期用"凭证"，规范要求"凭据"。`事实`促成因素是**边界扫描规则过宽**。

**具体动作与验收**

1. 清扫前**先核对实际消费者**在用什么词，而不是先信规范表。
2. 区分"仓库原本就有的分歧"与"清扫引入的新分歧"——后者必须回退。
3. 机械匹配规则要收窄，避免子串误伤（例如限定完整词与上下文）。
4. 技术词按类别保留原义，逐类裁定而不是全局替换。

**例外与失效条件**：确实无消费者的过时术语可以直接统一。

**现有防护与缺口**：回退 4 处分歧并修了规则。缺口：**浏览器视觉未验证**（HC18）。

**案例**：HC18。

## L11 状态描述必须绑定机器可判定的退出码

**触发条件**：写任何给 CI、外层脚本或 AI 判断的"状态""结论""BLOCKED/VERIFIED"报告。

**失败机制**：`事实`——既有报告写 BLOCKED 却 `exit 0`；新增的发布门缺凭据时 `exit 2`（HC13/N13）。`推断`促成因素是**状态是给人看的文字，机器读不了**。

**具体动作与验收**

1. 为每个状态建立**退出码契约**（例如 BLOCKED=2、VERIFIED=0、FAILED=1）。
2. 用脚本**实跑**每个分支，确认退出码与文字一致；不要只读代码。
3. 退出码与状态文字矛盾时，以退出码为失败处理。

**例外与失效条件**：纯人读文档没有退出码契约。

**现有防护与缺口**：缺凭据 exit 2 实跑通过。缺口：**hosted 未验**（N13）。

**案例**：N13。

## L12 spawn ENOENT 表示测试没跑，不表示产品失败

**触发条件**：验证脚本、包装入口、批量执行器启动失败。

**失败机制**：`事实`——Windows 包装入口 `spawn` 失败，整批验证被记为 `red-environmental`（N04）。`推断`促成因素是**把"入口起不来"与"测试红"混成一种状态**，后来另一路成功的结果容易被用来覆盖当次失败。

**具体动作与验收**

1. 保留"未运行"这一独立状态，不要改写成套件红或绿。
2. 修好入口后再执行；先前的失败记录保留，不追改。
3. 另一次的成功不能覆盖本次失败，两者是不同批次。

**例外与失效条件**：无。

**现有防护与缺口**：缺口：`事实`——后来另一路结果成功，但**不能覆盖当次失败**（N04）。

**案例**：N04。

## L13 统一预占预算，逐 attempt 建账；证据不能由字符串推断

**触发条件**：调用真实付费模型、真实上游服务，或需要出具"调用了多少次、成本多少"的报告。

**失败机制**：`事实`——原报告写"9 次真实调用"，混入误配置与未计数的退避；最终更正为 **10 个请求尝试**，其中只有 2 条（KNOW_REAL）有足够公网端点身份依据，其余 8 条为 UNKNOWN（HC10、HC12）。`事实`促成因素是**手写转述代替逐项原件**——provider 字符串不能证明公网调用。

**具体动作与验收**

1. 所有发送在**统一发送前预占预算**；失败、429、取消**不退款**。
2. 逐 `attemptId` 建账，逐条判定端点身份；判据不足就标 UNKNOWN，不推测。
3. 更正历史报告时**追加更正说明**，不改写旧结论的理由；保留不可恢复的帧缺口。

**例外与失效条件**：受控替身/mock 调用不计公网调用，但要显式标注为替身，不能混进真实调用计数。

**现有防护与缺口**：预算入口已修复。缺口：`事实`——**不能称"10 次公网调用"**；6 条历史帧不可恢复，仅 10:23 帧仍在（HC10、HC12）。

**案例**：HC10、HC12、HC13。

## L14 归因写"支持程度"，不写"确定根因"

**触发条件**：解释一个环境相关失败（超时、Access denied、ENOBUFS、并发失败），尤其在没有同条件对照实验时。

**失败机制**：`事实`——并发 30 超时、串行分别出现 memo 超时与 ENOBUFS、单独跑通过，却**没有同负载对照**就归因为机器负载（HC13）；esbuild 临时文件 Access denied 早期猜 SSD/权限，后续重定向 Temp 与时序对照才支持"外部扫描因素相关"（N09）。`推断`促成因素是**把相关性写成因果**，以及**假说没有随证据更新**。

**具体动作与验收**

1. 把**现象、可复现性、根因证据**分栏写，根因一栏在缺少对照时写"未验证"。
2. 用"同输入、不同环境"的对照实验区分候选原因，说明允许改动范围与停止条件。
3. 结论写成支持程度（相关／较强支持／确定），并保留反例。
4. 早期假说被推翻时**追加更正**，不删旧假说。

**例外与失效条件**：有对照实验且可重复时，可以给确定结论。

**现有防护与缺口**：HC13 归因已降为未验证、无源码改动。缺口：`事实`——**换机器或杀软环境仍可能复发**（N09）。

**案例**：HC13、N09。

## L15 成功隔离是反例，不要登记成故障；也别把反例升格为发布结论

**触发条件**：整理验证结果时，出现"结果符合预期"的结果。

**失败机制**：`事实`——迟到生成进入 `draft_candidates.jsonl`，第 1、2 章正文均不变（HC07）。这是**成功隔离**，不是正文污染事故。`推断`风险双向存在：登记为"发生过污染"会误导后续判断；反过来，把它写成"生成/取消/恢复都安全"则超出证据。

**具体动作与验收**

1. 成功反例单独归类，标注它证明了什么、没证明什么。
2. 结论严格限定在实测条件（这里的隔离场景），不外推到采纳、撤销、保存、恢复。
3. 复用既有证据，不为整理记录重复运行或扩大能力。

**例外与失效条件**：无。

**现有防护与缺口**：隔离探针与慢网取消记录支持该结论。缺口：**真实上游停止与计费未验**（HC07）。

**案例**：HC07。

## L16 批量清理按归属，不按日期

**触发条件**：任务开始前后要清理临时文件、缓存、产物目录，尤其是别人的残留也在同一目录时。

**失败机制**：`事实`——按日期清理**删除了会话开始前已存在的 4 个残留文件**（HC20）；而大输入在默认 Temp 下 8/8 失败、重定向后 8/8 通过。`推断`促成因素是**把"日期"当成本次创建的证明**，以及批量清理没有记录本次创建集合。

**具体动作与验收**

1. 记录**本次创建的集合**（创建时记录的路径清单），只清理该集合。
2. 保留外部残留；不要用"看起来是旧的"做删除依据。
3. 环境类失败先用重定向做对照实验再改代码。

**例外与失效条件**：独占的一次性目录可以按日期清理，但要在记录里写明该目录的独占性。

**现有防护与缺口**：构建两次通过。缺口：`事实`——**被删的 4 个文件没有恢复证据**（HC20）。

**案例**：HC20。

## L17 先清理生成内容前，定位它的写入者

**触发条件**：删除或改写由工具/生成器/同步器产出的文件内容，尤其是"清理"动作。

**失败机制**：`事实`——清理 CLAUDE 指针后，工具**再次追加**了一行指针；主会话改为 keep 块（HC18/N12）。`推断`促成因素是**只清理结果，没有确认生成器的重写行为**。

**具体动作与验收**

2. 模拟一次重写，再决定保留结构。
3. 清理后重新读取文件确认结果，不靠"命令执行成功"判断。

**例外与失效条件**：纯人工维护、无生成器介入的文件不需要本条。

**现有防护与缺口**：文档已调整。缺口：`事实`——**实际 analyze 未运行**（N12）。

## L18 副本与无消费者的抽象

**触发条件**：为了让两个消费方"共享"逻辑时，是否复制了整个文件；或打算添加一个"以后可能用"的工具模块。

**失败机制**：`事实`——为隔离 Web 与 pipeline 传播取消，产生了**两个约 1043 行的契约副本**，各自成为事实标准；进程树工具**无生产消费者**且有终止等待缺陷（HC09）。`推断`促成因素是**复制实现代替单一契约**，以及**按想象能力添加抽象**。

**具体动作与验收**

1. 保留**单一契约源**；需要差异时用参数或薄适配层，不用整文件复制。
2. 新增工具模块前先确认**至少一个真实生产消费者**；没有消费者的模块不进主干。
3. 抽象以"真实取消传导"验收，不以"测试通过"验收。

**例外与失效条件**：跨运行时/跨进程确有不可共享边界时，复制可接受，但必须在记录里写明为什么不能共享。

**现有防护与缺口**：后续收口已删除并缩小验收范围。缺口：`事实`——**本轮未复测**（HC09）。

**案例**：HC09。

## L19 原子发布：草案存在 ≠ 正式发布成功

**触发条件**：任何"写入 → 原子替换 → 删除临时文件"的发布/落盘流程，尤其在 Windows 上。

**失败机制**：`事实`——`RENAME_NOREPLACE` 不支持时 `EINVAL`，正式目标不存在，草案与临时文件却保留（HC09/N01）。`推断`促成因素是**假设平台具备原子发布能力而未先用探针验证**。

**具体动作与验收**

1. 把**正式路径存在**、**内容回读**、**失败清理**列为发布验收三件事。
2. 先用探针验证平台是否支持所用的原子语义，再依赖它。
3. 不支持时设计降级路径（直接写入 + 回读校验），并把降级写进记录。

**例外与失效条件**：有备份且可回滚的简单覆盖写可以接受，但必须配回读校验。

**现有防护与缺口**：`事实`——生产未实施，**交付被阻断**（N01）。

**案例**：N01。

## L20 短写与零进展：writeSync 返回值必须被检查

**触发条件**：任何原子写作者正文/文件的代码路径。

**失败机制**：`事实`——单次 `writeSync` 被当作完整写入；短写注入允许只写部分字节，且**恒返回 0 也未显式失败**（HC04）。`推断`促成因素是**正常完整写掩盖了异常路径**。

**具体动作与验收**

1. 按**返回字节数循环写满**，直到写完或返回 0。
2. 返回 0 且未写完时**显式失败**并清理临时文件。
3. 用短写与零进展注入做回归测试，确认由红转绿。

**例外与失效条件**：写设备保证原子整写的场景可豁免，但需在代码注释里写明依据。

**现有防护与缺口**：短写 3 字节与零进展测试已由红转绿。缺口：`事实`——**本轮未复测**（HC04）。

**案例**：HC04。

## L21 环境判断与 mock 门禁要成对

**触发条件**：区分"开发可用"与"生产可用"；代码里有多个形态相近的开关或 mock 入口。

**失败机制**：`事实`——`mock-empty` 分支有生产闸，**同函数的 mock 分支没有**（HC05）；OCR 审查模式复用只得到 partial，真实付费上游未验证（N03）。`推断`促成因素是**只检查已知开关而未枚举同族入口**，以及**分支命名制造了安全感**。

**具体动作与验收**

1. 枚举**同族**入口（同一函数的多个 mock/分支），逐个确认生产恒为 false。
2. 生产与非生产两侧都要有测试（当时是 3 项，2 红 → 3 绿）。
3. 扫描/并发通过不等于真实上游通过；输入识别、审查决策、取消传导、真实提供方分别取证。

**例外与失效条件**：不进入生产构建路径的测试替身可豁免。

**现有防护与缺口**：3 项测试已修复。缺口：`事实`——**真实付费上游未验证**（HC05、N03）。

**案例**：HC05、N03。

## L22 修正错误的测试策略，而不是改引擎迎合测试

**触发条件**：测试与生产接线不一致时，先判断是"测试错了"还是"引擎错了"。

**具体动作与验收**

1. 先确认**消费者和执行流**，再判断该改哪一侧。
2. 补最小接线与**反例**（反例失败才算测试有效）。
3. 图谱缺失或接线未确认时，明示"未过图谱门禁"，不因新测试通过而放行。

**例外与失效条件**：无。

**现有防护与缺口**：27 项新测试、16 项回归通过。缺口：`事实`——**明示未过图谱**（N02）。

**案例**：N02、N05。
