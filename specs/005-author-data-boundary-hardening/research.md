# Phase 0 Research: 作者数据完整性与出站边界加固

**Feature**: `005-author-data-boundary-hardening` | **Date**: 2026-10-12

Technical Context 无 `NEEDS CLARIFICATION` 项（技术栈与约束由既有仓库决定）。本文件记录本轮**真实做过的技术取舍**及其备选，供后续读者判断「为什么这么做」。

---

## R1 出站地址绑定如何实现（不新增依赖）

- **Decision**: 用 Node 内置 `node:https` / `node:http` 的 `lookup` 注入，把连接固定到已验证的解析地址；URL 的 host 保持不变。
- **Rationale**: 保留原域名的 Host 头、TLS SNI（`servername` 默认取 hostname）与证书校验对象，同时消除「校验一次、连接时再解析一次」的 TOCTOU。
- **Alternatives considered**:
  1. **给原生 `fetch` 传 `dispatcher`**（undici 的 `Agent` 支持自定义 `connect.lookup`）——本仓 `undici` 不是依赖（`pnpm-lock` 里只有 `undici-types`），`require('undici')` 实测 `MODULE_NOT_FOUND`；采用它需新增依赖，与「不新增依赖」约束冲突。
  2. **把 URL 换成 IP 直连**——会丢掉 Host 与 SNI，证书校验对象改变，方案明确禁止。
  3. **只在发请求前再查一次 DNS**——仍是两次独立解析，未关闭窗口。
  4. **引入 `undici` 作为依赖**——最小可用，但为单一用途引入运行时依赖，且会替换全局 fetch 语义；不采用。

## R2 账本追加失败后的处置

- **Decision**: 追加失败即置「停止发布」标记（毒化），并要求调用方按账本核对后经恢复入口解锁；恢复入口**先**核对账本物理完整性（每个非空行可解析且末行以换行结束），核对与重建都成功才解除停止。
- **Rationale**: I/O 抛错可能已写入部分字节，结果不明——按「完全没写」重试会让后续 append 把新行粘到半行之后，把可诊断的损坏固化成永久坏行（隔离复现已复现）。
- **Alternatives considered**:
  1. **按「完全没写」直接重试**——最小改动，但会把损坏固化；且内存配对状态若已更新会与账本分叉。
  2. **自动修复尾部**（截断到最后一个完整行）——需要证明「被截断的正是本次追加」，而失败时结果不明，无法证明；且截断是破坏性操作。
  3. **跳过所有坏行后宣称恢复成功**——把损坏隐藏为成功，最危险。
  4. **恢复时保留审计读的容错（跳过撕裂行）**——恢复入口不能沿用审计读的容忍口径，两者目标相反。

## R3 采纳意图的格式扩展方式

- **Decision**: 同一文件、同一目录，`schemaVersion` 由 1 升为 2，新增**可选** `operation` 块；读取端同时接受 1 与 2，缺块按「旧记录」处理。
- **Rationale**: 意图文件是崩溃恢复的唯一凭证，改路径会丢掉既有在途记录；加可选字段是唯一不破坏既有记录的扩展方式。
- **Alternatives considered**:
  1. **新目录 / 新文件名**——既有在途意图会被当成不存在，恢复能力直接丢失。
  2. **升版本但只接受 v2**——存量 v1 记录读取即报损坏，等于把历史记录判死。
  3. **不加版本号，只加字段**——可行但无法在读取端表达「这是新格式」，且违背方案「明确格式版本」的要求。

## R4 崩溃恢复补写结果时的身份来源

- **Decision**: 补写操作结果时，身份一律取自**意图中保存的原始操作身份快照**；补全函数不接受当前请求。
- **Rationale**: 恢复窗口（结果已写/未写、任务关联已写/未写）里，重试请求可能是另一个主体或另一个操作标识；用请求身份补写等于把别人的操作认成自己的。
- **Alternatives considered**:
  1. **沿用请求携带的操作标识**——即修复前的行为，产生跨主体回放缺口。
  2. **从正文哈希反推请求身份**——方案明确禁止（哈希不是身份）。

## R5 内容编码解码放在哪一层

- **Decision**: 放在出站传输层，流式读取与整体读取共用同一条解码路径；未支持的编码显式失败。
- **Rationale**: 原生 `fetch` 透明解压，换成 `node:https` 后必须补回，否则流式内容解析出零条、网页内容变成压缩乱码（独立验收已实测两者）。放在传输层使所有调用方（模型、爬虫、检索）一次性受益，避免「只给流式加特例、爬虫继续读乱码」。
- **Alternatives considered**:
  1. **只在流式路径加解压**——爬虫与整体读取仍读乱码（被独立验收点名的形态）。
  2. **只发 `Accept-Encoding: identity` 来规避解压**——上游/网关可能无视该声明仍压缩；且改变了与既有实现的协商行为。
  3. **不解压，把压缩字节交给调用方**——即把乱码当正文。

## R6 候选写锁的临界区粒度

- **Decision**: 只圈候选的读-改-写（建候选、追加增量、结束流、取消结算），**模型等待留在锁外**。
- **Rationale**: 整段生成持锁会让同书其他写入（保存别章、备份）被整段生成阻塞；而候选落盘本身是短本地 I/O。
- **Alternatives considered**:
  1. **整段生成持锁**——正确性最高但可用性最差，且方案明确要求模型等待在锁外。
  2. **不给生成路径接锁**（只给采纳/取消接锁）——留下列的丢更新窗口；不采用，但以可选注入实现，未注入时行为与改前逐字相同。

## R7 取消检查的时机

- **Decision**: 外部取消信号在**第一次等待之前**绑定，并在每个等待点（解析后、取锁后、每次读块与每条已缓冲事件之前）复查。
- **Rationale**: 只在流程入口检查会漏掉「等待期间取消」这一类窗口（隔离复现与独立验收各复现过一个）。
- **Alternatives considered**:
  1. **只在入口检查**——漏掉等待窗口（即修复前的形态）。
  2. **依赖底层传输在取消时抛错**——已缓冲的内容仍会产出；且抛错会走失败分类而非取消分类。
