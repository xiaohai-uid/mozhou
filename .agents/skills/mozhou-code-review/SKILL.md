# mozhou-code-review

墨舟项目专属代码审查标准。开 PR 前自查、或用户要求 review 时调用。
通用开发流程走 spec-kit；这份 skill 是"本项目的尺子"，只关心墨舟的规矩。

## 审查维度（按顺序过）

### 1. 工单边界（UVSD §2）

- 一次改动是否只实现一个可观测行为？
- 有没有顺手重构、跨模块改动、目录重组？
- 有没有提前做 V2/V3 抽象、"以防万一"的扩展点？（UVSD §1.4：不许臆测）

### 2. 契约一致性（UVSD §3）

- 动了契约？有没有配套的 Contract Delta（schema + mock + 实现 + 测试四件套同步）？
- 有没有用 `any`、未类型化 map、未文档化字段绕过契约？

### 3. 测试完整性（UVSD §5）

- 每个行为变更有没有对应测试？
- 有没有为了让验证通过而改弱、删除、跳过测试？（§20：绝不允许）
- 现有通过的测试是否被当作回归约束保留？（§21）

### 4. 反 AI 味清单（逐条过，不许跳）

1. **重复规则**：同一条规则出现两处以上 → 只留一处，其余改成链接
2. **推理实录**：删掉"我是这样一步步推导出来的"过程叙述，只留结论和契约
3. **强调通胀**：满屏加粗 / 大写 / 感叹号 = 没有重点；一屏只允许一个视觉重点
4. **段落墙**：一个段落塞多条规则就拆成列表
5. **状态标注腐烂**：不写"已实现！""TODO：未来支持…"这种会过期的断言；状态只活在工单和 CI 里
6. **手写复述机器可生成之物**：能从类型 / 代码生成的表格、目录，不手写第二份
7. **注释复述代码**：删掉把代码翻译一遍的注释；注释只写"为什么"，不写"是什么"
8. **防御性冗余**：类型系统已保证的东西，不再加运行时检查
9. **注释掉的代码**：删，不许留"万一以后用得上"
10. **残留物**：无用导入、`console.log`、调试开关、临时 mock

### 5. 呈现

- 新增工具 / 接口 / 错误信息时，UI 呈现是否合理（字段名用户看得懂吗？报错信息能指导操作吗？）

## 输出格式

按严重程度分级：`阻断` / `建议` / `nit`。
每条注明文件:行号 + 一句话原因 + 具体改法。先列阻断项，再列建议。
没有阻断项就明确说"可合入"，不许模棱两可。
