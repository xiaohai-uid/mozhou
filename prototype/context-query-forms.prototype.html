调用方式：queryActiveFacts(chapterIndex, entityIds, pov) → compile(taskType, scope, budget, …) → { packet, receipt, manifest }。 视角与区间是缝的签名参数——调用方没法"忘传"，编译器统一强制。 草稿提及驱动激活；钉选走 manual_pin；图一跳自动扩展进「关联召回」层。
调用方式：作者写一段引用配方（每条 @ 引用 = 一条可静态提取的依赖声明），展开器单遍非递归展开； 解析失败显性化成红牌 + [Error] 行，其余行继续。注意：方案 B 不看草稿提及—— 进什么完全由配方决定（这正是差异点之一）。

两侧都跑一遍后值得拍板的议题（供 grilling）

  • 泄漏防线放在哪一层？ A 里"知情=pov"是查询签名的强制参数，不存在"忘写"这个错误类别； B 里它是配方里的一节过滤器——作者每处都要自觉，漏一处就是全量泄密（见走查二的红牌）。 防线强度 vs 表达自由的取舍怎么定？
  • 错误何时暴露？ B 的引用写错在运行期得到响亮的 ParseFailure 红牌； A 的拼写错被编码期类型系统拦住，但运行期传错 ID 只是安静地空结果——审计面上只表现为清单变短。 你更怕哪一种静默失败？
  • 依赖清单何时可知？ B 每条 @ 引用在展开前就能静态提取成 Dependency Manifest 声明（变更影响分析可提前到保存配方时）； A 的清单是执行后的读账。提前声明值多少钱？
  • "正文提到了谁"由谁发现？ A 由草稿提及（关键词激活）驱动；B 完全由配方声明。 网文写作流里，作者愿意手工维护"本章要哪些设定"吗，还是要 Codex 式 Detected 自动命中？
  • 谁来写这些调用？ A 的受众是写代码的人（类型、IDE 补全）；B 的受众可能是高级作者/模板作者（类 lorebook 手感）。 墨舟 Phase 2 的真实调用方是产品功能还是作者模板？
  • 混合形态值不值得开票？ 研究卷二 D.4 的暗示：声明式做"配方/模板层"，底层仍是确定性查询算子， 配方里的 @ 引用静态提取进 Manifest、知情过滤下沉为算子默认行为。若走混合，边界画在哪？
  • 与冻结约束的咬合： 两案都能产出 ReceiptEntry(AssemblyChannel/ExclusionReason)/ParseFailure/recomputationHash， 都满足服务端装配（N10）。差异不在能不能，而在错误分布与维护成本。
